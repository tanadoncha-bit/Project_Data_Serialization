# CookHub — แพลตฟอร์มสูตรอาหารและคอร์สเรียนทำอาหาร

CookHub เป็นเว็บแอปพลิเคชันสำหรับค้นหาสูตรอาหารและเรียนทำอาหารผ่านวิดีโอ ผู้ใช้สามารถบันทึกรายการโปรด ซื้อสูตรหรือคอร์ส และเขียนรีวิว ส่วนเชฟสามารถสร้างสูตร จัดการบทเรียน รวมคอร์สเป็นแพ็ก และดูข้อมูลการขายผ่าน Dashboard

**เว็บไซต์:** [cookhub-kz00.onrender.com](https://cookhub-kz00.onrender.com/home)

## ความสามารถของระบบ

### ผู้ใช้ทั่วไป

- ค้นหาและกรองสูตรอาหารหรือคอร์สเรียน
- ดูสูตรอาหารจากผู้เผยแพร่ในระบบและแหล่งข้อมูล TheMealDB
- เพิ่มและนำสูตรหรือคอร์สออกจากรายการโปรด
- เข้าถึงเนื้อหาตามสิทธิ์ของสูตร คอร์สเดี่ยว และแพ็กคอร์ส
- ดูวิดีโอบทเรียน พร้อมสูตรประกอบที่แสดงวัตถุดิบและวิธีทำเมื่อมีสิทธิ์เรียน
- ให้คะแนนและเขียนรีวิวตามสิทธิ์ โดยรีวิวสูตรและคอร์สแยกจากกัน
- แก้ไขโปรไฟล์ อัปโหลดรูป ยืนยันอีเมล และตั้งรหัสผ่านใหม่
- ใช้งานผู้ช่วย AI ด้านการทำอาหารเมื่อกำหนดบริการ AI แล้ว

### เชฟ

- สร้าง แก้ไข และลบสูตรอาหารของตนเอง
- สร้างคอร์สจากสูตรต้นทาง เพิ่มชื่อบทเรียน ลิงก์วิดีโอ และระยะเวลา
- รวมคอร์สเดี่ยวเป็นแพ็กคอร์ส
- ดู Dashboard สรุปคอร์ส สูตร ผู้เรียน ยอดซื้อ และรายการสั่งซื้อ
- ดูรายการแจ้งเตือนการซื้อและรีวิวที่เกี่ยวข้องกับผลงานของตนเอง

## การติดตั้งและรันในเครื่อง

ต้องมี Node.js 24.x, npm และฐานข้อมูล MongoDB ที่เชื่อมต่อได้

1. ดาวน์โหลดโปรเจกต์และติดตั้ง dependencies

~~~bash
git clone https://github.com/tanadoncha-bit/Project_Data_Serialization.git
cd Project_Data_Serialization/recipehub
npm ci
~~~

2. สร้างไฟล์ .env ในโฟลเดอร์ recipehub และกำหนดค่าพื้นฐาน

~~~dotenv
NODE_ENV=development
PORT=3000
APP_URL=http://localhost:3000
MONGODB_URI=<MongoDB connection string>
SESSION_SECRET=<ค่าสุ่มอย่างน้อย 32 ตัวอักษร>
~~~

3. เพิ่มค่าบริการที่ต้องการใช้ตามตารางถัดไป แล้วเริ่มเซิร์ฟเวอร์

~~~bash
npm run dev
~~~

เปิด http://localhost:3000 หากต้องการรันโดยไม่ใช้ nodemon ให้ใช้ npm start

## สถาปัตยกรรมและการไหลของข้อมูล

ระบบใช้ Express แบ่งหน้าที่เป็น routes, services และ models ส่วนหน้าเว็บสร้างด้วย EJS และเพิ่มการโต้ตอบด้วย JavaScript

~~~text
ผู้ใช้ / เชฟ
    ↓ HTTP Request
Express Routes → Middleware ตรวจบัญชี สิทธิ์ และข้อมูล
    ↓
Services → Mongoose Models → MongoDB
    ↓
EJS HTML หรือ JSON Response → Browser
~~~

บริการภายนอกเรียกจากฝั่งเซิร์ฟเวอร์ เพื่อไม่ให้คีย์ลับปรากฏใน JavaScript ที่ส่งให้เบราว์เซอร์

## โครงสร้างข้อมูลและความสัมพันธ์

| Model | ข้อมูลหลัก | ความสัมพันธ์ |
| --- | --- | --- |
| Client | บัญชี บทบาท โปรไฟล์ และสถานะอีเมล | เป็นผู้เผยแพร่สูตร/คอร์ส ผู้ซื้อ และผู้เขียนรีวิว |
| Recipe | ชื่อ รูป หมวดหมู่ วัตถุดิบ ขั้นตอน และราคา | publisher อ้างถึง Client |
| SingleCourse | ชื่อ ราคา รายละเอียด และวิดีโอบทเรียน | publisher อ้าง Client; baseRecipe อ้าง Recipe |
| MultiCourse | ชื่อ รายละเอียด ราคา และคอร์สในแพ็ก | publisher อ้าง Client; includedCourses อ้าง SingleCourse หลายรายการ |
| Transaction | ผู้ซื้อ ประเภทสินค้า รหัสสินค้า และยอดชำระ | buyer อ้าง Client; itemType และ itemId ระบุสูตรหรือคอร์สที่ซื้อ |
| Favorite | ผู้ใช้ ประเภท และรหัสรายการโปรด | client อ้าง Client; itemType และ itemId ระบุรายการที่บันทึก |
| RecipeReview | ผู้เขียน คะแนน ความคิดเห็น และเวลา | client อ้าง Client; recipeType และ recipeId แยกสูตรภายใน/ภายนอกและคอร์สแต่ละประเภท |
| PaymentOrder / CoursePaymentOrder | สถานะคำสั่งชำระเงินและข้อมูลอ้างอิงผู้ให้บริการ | ใช้ตรวจสอบการชำระเงินก่อนให้สิทธิ์ผ่าน Transaction |

Recipe เก็บวัตถุดิบและขั้นตอนเป็น embedded arrays ส่วนคอร์สเดี่ยวเก็บวิดีโอบทเรียนเป็น array ภายใน document ข้อมูลที่ต้องใช้ร่วมกัน เช่น เจ้าของ สูตรต้นทาง และคอร์สในแพ็ก ใช้ reference แทนการคัดลอก document ทั้งชุด

คะแนนรีวิวคอร์สคำนวณจากรีวิวของคอร์สนั้น ไม่ใช้คะแนนของสูตรต้นทางหรือคะแนนคอร์สอื่นแทน

## การจัดรูปแบบและรับส่งข้อมูล

- คำขอแบบ fetch ใช้ JSON ตาม endpoint เช่น รายการโปรดและผู้ช่วย AI
- ฟอร์มทั่วไปส่ง application/x-www-form-urlencoded; รูปภาพส่ง multipart/form-data
- MongoDB เก็บข้อมูลเป็น BSON และ Mongoose ใช้ schema เพื่อตรวจชนิดข้อมูลและความสัมพันธ์
- services แปลงผลจากฐานข้อมูลหรือ API ภายนอกเป็นข้อมูลสำหรับหน้าเว็บ ก่อนส่งต่อให้ EJS หรือ JSON response
- ส่วนรีวิวโหลดเป็น HTML fragment จึงปรับเฉพาะส่วนรีวิวได้โดยไม่โหลดทั้งหน้าใหม่
- รหัสผ่านเก็บเป็น hash ส่วน token ยืนยันอีเมลและรีเซ็ตรหัสผ่านเก็บแบบ hash พร้อมเวลาหมดอายุ

## ข้อจำกัดของการตั้งค่าปัจจุบัน

- การรับเงินจริงยังปิดอยู่ ต้องตั้งบัญชีผู้ให้บริการ คีย์ และตรวจเส้นทางชำระเงินก่อนเปิดใช้
- production ไม่นับสิทธิ์ซื้อแบบ demo หรือ gateway-test และไม่เปิดการซื้อจำลอง
- รูปโปรไฟล์เก่าที่ไฟล์ต้นฉบับหาย ต้องให้เจ้าของบัญชีอัปโหลดใหม่
- สถานะอ่านแจ้งเตือนเก็บในเบราว์เซอร์ จึงไม่ซิงก์ข้ามอุปกรณ์
- การส่งอีเมลและการใช้งาน AI ขึ้นกับการอนุมัติบัญชี โควตา และการตั้งค่าของผู้ให้บริการ

## การตรวจโค้ดอัตโนมัติ (CI)

GitHub Actions รันบน Node.js 24 เมื่อ push เข้า main/recipe หรือเปิด Pull Request เข้า branch เหล่านี้ โดยติดตั้งเฉพาะ production dependencies ด้วย npm ci --omit=dev แล้วตรวจ JavaScript, คอมไพล์ EJS, การอ้างอิงโมดูลและไฟล์หน้าเว็บ และตรวจช่องโหว่ dependency ระดับ high/critical โดยไม่ต้องใช้ฐานข้อมูลหรือคีย์ลับ

รันในเครื่องได้ด้วย:

~~~bash
cd recipehub
npm run check
npm run audit:production
~~~

CI นี้ยังไม่ใช่การทดสอบฟีเจอร์ครบระบบ ไม่ครอบคลุมการรับส่งอีเมล การชำระเงิน และการเชื่อมต่อฐานข้อมูลจริง

render.yaml กำหนดให้ติดตาม main และ deploy หลัง CI ผ่าน สำหรับบริการ Render ที่สร้างผ่านหน้า Web Service ให้ตั้ง Settings → Build & Deploy → Auto-Deploy เป็น After CI Checks Pass ด้วยตนเอง การเปลี่ยน YAML อย่างเดียวไม่อัปเดตบริการที่ไม่ได้เชื่อม Blueprint

## ประวัติการเผยแพร่บน GitHub

Workflow Sync Render Deployment ตรวจ /healthz ของเว็บจริงทุกประมาณ 30 นาที หรือกด Run workflow เองได้ แล้วบันทึก GitHub Deployment ใน environment production ตามรหัส commit ที่ Render รันอยู่จริง ไม่ใช้เพียงผล CI เพื่อสรุปว่า deploy แล้ว

งานนี้แยกจาก CI และไม่ trigger ตอน push เพื่อไม่ให้ Render ซึ่งรอ CI ต้องรอ workflow ที่กำลังรอการ deploy อีกทอด ใช้ GITHUB_TOKEN ของ Actions ที่มีสิทธิ์เขียน deployments โดยไม่ต้องเพิ่ม Render API key หรือ Deploy Hook

หากเว็บไม่พร้อมหรือยังไม่ส่งรหัส revision ระบบจะไม่บันทึกว่า deploy สำเร็จ ตารางเวลาของ GitHub อาจมีความล่าช้า และการตรวจเว็บอาจปลุกบริการ Render Free ที่พักอยู่
